# 离散数学智能助教 Agent 项目说明

本项目面向离散数学课程，目标是构建一个同时服务学生与教师的智能助教系统。系统不仅提供基于课程讲义/PPT 的问答能力，还覆盖班级管理、课程资料管理、作业发布与提交、多轮会话、学习报告、班级反馈和后台管理等教学场景。

当前项目采用前后端分离架构：前端使用 React + Vite，后端使用 FastAPI，Agent 核心作为 `backend/agent_core` 子模块独立维护。Agent 通过自研 ReAct 流程调用课程知识检索、课程管理查询、图像理解、学情分析等工具；课程知识库使用 Qdrant 向量检索 + BM25 关键词检索 + RRF 融合排序的混合 RAG 方案。

---

## 一、当前进度与主要改进

### 1. 整体架构已经从早期原型演进为完整教学系统

项目目前已经形成较清晰的三层结构：

- **前端展示层**：负责用户登录、角色选择、聊天交互、资源管理、作业管理、学习报告展示和后台页面。
- **业务后端层**：负责认证鉴权、班级/课程/作业/会话/学情等业务接口，并将用户请求组织为 Agent 可消费的上下文。
- **Agent 核心层**：作为独立子模块维护，负责模型调用、工具选择、RAG 检索、图像分析和最终回答生成。

这种拆分比早期“单一 Agent workflow”更适合后续多人协作：业务功能可以在后端迭代，Agent 能力可以在子模块中独立优化，前端体验也可以按页面和组件逐步拆分。

### 2. Agent 能力已经具备可扩展的 ReAct + Tool 形态

Agent 核心位于 `backend/agent_core`，目前已经不是简单的 if-else 问答流，而是通过自研 ReAct 循环完成：

1. 读取用户问题、会话上下文和可用工具描述。
2. 由模型判断是否需要调用工具。
3. 执行课程知识检索、课程管理查询、图像分析或学情工具。
4. 将 Observation 回填给模型继续推理。
5. 输出最终 Markdown 答案。

当前主要工具包括：

- `query_lecture_knowledge`：检索课程讲义/PPT，并返回文件名、页码和相关内容。
- `query_course_admin`：查询结构化课程、班级、作业等管理信息。
- `analyze_uploaded_image`：分析用户上传的题目截图或图形内容。
- 学情相关工具：生成学生个人报告和班级学习反馈。

### 3. RAG 检索链路已经升级为混合检索

课程知识库当前支持 PDF、PPTX/PPSX 等资料入库。处理流程大致为：

1. 解析课程资料并按页或幻灯片切分为文本块。
2. 保存来源文件、页码、章节、材料归属等元数据。
3. 使用 Embedding API 写入 Qdrant 向量库。
4. 使用 Jieba + BM25 建立关键词索引。
5. 查询时向量检索和 BM25 各取 `2 * TOP_K` 条候选。
6. 使用 RRF 融合排序，最终返回 `TOP_K` 条结果。

当前 `TOP_K` 配置在 `backend/agent_core/config/settings.py` 中，默认值为 `3`。也就是说每次混合检索最终返回 3 个课程片段，向量和 BM25 各自先召回 6 个候选片段用于融合。

### 4. 答案呈现已经支持课程来源、Markdown、LaTeX 和 Mermaid

前端已经使用统一的 Markdown 渲染组件承接模型输出，支持：

- Markdown 段落、标题、列表、表格等结构化排版。
- LaTeX 行内公式和块级公式。
- Mermaid 图表，用于集合关系、Hasse 图、树、流程图等离散数学可视化内容。
- 按 RAG 命中结果标注讲义/PPT 来源和页码。

这解决了早期回答中公式以原始 LaTeX 文本直接显示的问题，也让 Agent 可以在回答离散数学问题时更自然地展示推导、公式和图结构。

### 5. 前端已经从单一页面逐步拆分为业务页面和组件

前端当前位于 `frontend/src`，主要结构包括：

- `app/App.jsx`：应用级状态、路由和核心业务编排。
- `pages/ChatPage.jsx`：聊天主页面。
- `pages/ResourcesPage.jsx`：课程资源页面。
- `pages/HomeworkPage.jsx`：作业页面。
- `pages/AdminUsersPage.jsx`：后台用户管理页面。
- `components/chat`：聊天输入、消息展示、历史会话侧栏等组件。
- `components/modals`、`components/layout`、`components/scenes`：弹窗、布局和视觉场景组件。
- `api`：前端 API 调用封装。
- `utils`：文件类型、附件校验、客户端消息 ID、日期时间等通用逻辑，并已配套部分单元测试。

相比早期版本，前端不再只是一个演示 UI，而是已经承载了较完整的教学使用流程。

### 6. 后端业务模块已经覆盖主要教学闭环

后端当前位于 `backend`，核心模块包括：

- `app/interfaces/api`：FastAPI 路由层，包含认证、班级、聊天、会话、作业、学情、附件、后台管理等接口。
- `app/core`：认证、依赖注入、Agent 绑定、Redis、邮件、文件存储、Mermaid 服务等基础能力。
- `app/services`：会话上下文、聊天附件、学习报告、长期记忆等服务逻辑。
- `database`：MySQL、课程、班级、作业、会话、学情、记忆和向量仓库访问层。
- `scripts`：资料入库、RAG 评测、性能评测、存储路径迁移、调试密码重置等脚本。
- `tests`：RAG scope、聊天流式输出、作业附件、学习报告、后台管理、健康检查等测试。

目前系统已经具备从“教师上传资料”到“学生问答”、从“作业发布提交”到“学情分析反馈”的基本闭环。

### 7. 数据与部署能力进一步完善

当前项目依赖以下主要基础设施：

- MySQL：保存用户、班级、课程资料、作业、会话、反馈、学习报告等业务数据。
- Redis：用于邮箱验证码、频率控制等短期状态。
- Qdrant：保存课程知识向量索引。
- 本地文件系统：保存课程资料、聊天附件、作业附件、解析后的 chunk、BM25 索引和日志。
- GitHub Pages：用于前端页面自动部署。
- Docker Compose：用于生产部署编排，具体配置在 `compose.production.yml`。

后端已经引入 Alembic 迁移脚本，说明数据库结构开始走向可追踪、可演进的形态。

## 二、基于当前代码的修改与完善建议

### 1. 继续收敛前端 App 层职责

前端虽然已经拆出了页面和组件，但 `frontend/src/app/App.jsx` 仍然承担了大量全局状态、业务操作、路由跳转和副作用逻辑。后续建议：

- 将认证状态、班级状态、会话状态、作业状态、学情状态分别拆成独立 hooks 或 context。
- 将 API 调用后的数据归一化逻辑移出页面层。
- 保持 `App.jsx` 只负责应用框架、路由和顶层状态装配。

这样可以降低后续新增页面时的冲突概率，也更方便单元测试和局部重构。

### 2. 强化 RAG 的可观测性与可调参能力

当前混合 RAG 已经具备向量 + BM25 + RRF 的基础形态，但仍建议继续完善：

- 将 `TOP_K`、向量召回倍数、BM25 召回倍数、RRF 参数暴露为明确配置。
- 在回答日志中记录每次命中的文件名、页码、分数、召回来源和最终排序。
- 区分“未入库”“入库但未召回”“召回但被模型忽略”三类问题。
- 为典型课程问题建立固定评测集，持续比较不同检索参数的命中率和答案质量。

这部分对排查“评测脚本能命中，但用户界面提示未找到”的问题尤其重要。

### 3. 完善资料入库状态与管理界面

当前资料入库依赖脚本和后端处理链路，建议在教师端补充更明确的状态反馈：

- 每个资料显示是否已上传、是否已解析、是否已写入 Qdrant、是否已写入 BM25。
- 展示 chunk 数量、页码范围、最后入库时间和失败原因。
- 支持对单个资料重新入库、删除索引、清空并重建索引。
- 对 `backend/storage/processed/chunks`、BM25 JSON 和 Qdrant collection 做一致性检查。

这可以让教师和开发者更容易判断“资料在 raw 里”和“资料真正可被 RAG 检索”之间的差异。

### 4. 进一步规范 Agent 输出协议

当前前端已经支持 Markdown、LaTeX 和 Mermaid，Agent prompt 也已经要求标注来源。后续建议把输出协议继续固化：

- 明确多意图问题的回答结构，例如每个子问题开头统一列出“来源”。
- 对无来源回答统一标注“未命中课程资料，以下基于通用离散数学知识回答”。
- 对 Mermaid 输出建立自动校验或失败回退机制，避免前端渲染失败。
- 将来源信息尽量从工具结构化结果传递到最终回答，而不是完全依赖模型复述。

长期看，可以考虑让后端返回 `answer + citations + render_blocks` 的结构化响应，再由前端负责稳定渲染。

### 5. 加强鉴权、配置和密钥安全

项目已经经历过 `.env` 和历史记录清理，后续建议将安全规范写入开发流程：

- 所有 `.env`、虚拟环境、数据库文件、日志和本地存储都必须保持 ignore。
- 提供 `.env.example`，只保留变量名和说明，不放真实密钥。
- 在 CI 或 pre-commit 中加入 secret scan。
- 生产环境中收紧 CORS，只允许真实前端域名。
- 定期轮换 API Key、JWT Secret、数据库密码和 SMTP 密码。

这部分不只是代码问题，也会直接影响项目能否安全公开部署。

### 6. 补齐后端测试与端到端验证

当前后端和前端都已经有一部分测试，但建议进一步形成稳定的质量门槛：

- 后端补充 API 层集成测试，覆盖认证、班级、课程资料、作业、聊天、附件权限等关键路径。
- 前端补充页面级交互测试，尤其是聊天流、附件上传、公式渲染、Mermaid 渲染和角色权限展示。
- RAG 评测脚本纳入固定数据集，形成可重复的检索质量报告。
- 为数据库迁移脚本增加从空库到当前 schema 的验证流程。

最低目标是每次合并前都能执行：前端 lint/test/build、后端 pytest、RAG smoke test。

### 7. 清理历史依赖和编码问题

当前依赖和部分文档/注释中仍能看到早期迭代痕迹，建议逐步处理：

- 清理不再使用的依赖，例如历史遗留的向量库或异步 Redis 包。
- 锁定后端依赖版本，避免部署环境漂移。
- 检查中文文件的编码，统一使用 UTF-8，避免 README、架构文档或注释在不同终端中乱码。
- 对配置字段去重，例如重复路径、过期默认值、开发环境默认密钥等。

这类工作不一定带来新功能，但会明显提升项目可维护性。

### 8. 明确下一阶段优先级

建议下一阶段按以下顺序推进：

1. **稳定资料入库和 RAG 命中链路**：先保证课程资料可查、可解释、可复现。
2. **固化回答来源和渲染协议**：让用户能清楚知道答案来自哪份资料、哪一页。
3. **拆分前端 App 状态**：减少新增功能时的复杂度和冲突风险。
4. **补齐自动化测试与 secret scan**：让后续协作更安全。
5. **完善教师端运营能力**：资料状态、作业统计、学情反馈、班级管理继续细化。
6. **优化 Agent 工具选择与多轮上下文**：减少误检索、误调用和答非所问。

## 总结

项目已经从早期的离散数学问答 Agent 原型，发展为一个覆盖“资料入库 - 课程问答 - 作业提交 - 学情反馈 - 班级管理”的教学助教平台。当前最值得继续投入的方向，不是单纯增加页面或堆叠工具，而是把 RAG 可观测性、答案来源协议、资料入库状态、前端状态拆分和安全测试体系打牢。这样后续无论继续扩展课程、接入更多教师，还是部署到真实教学环境，项目都会更稳。
